# 法律法规问答助手：完整链路设计（优化版）

当前范围：**两模块**——RAG 离线建库、RAG 在线检索生成。高频问答（MySQL / BM25 直出）已砍掉，法律咨询一律走 RAG。流程图见 `流程图.md`。

---

## 一、总览

### 1.1 模块职责

| 模块 | 作用 | 是否调用大模型 | 数据存储 |
|------|------|----------------|----------|
| RAG 离线 | 法规解析、按条分块、BGE-M3 稠密/稀疏编码、写入知识库 | 否（清洗可另说，非问答主路径） | Milvus + 文档元数据 |
| RAG 在线 | 意图分流、问题治理、混合检索、重排、按检索内容生成 | 是（分流/改写/生成，可分级） | 读 Milvus；写对话日志 |

核心原则：

- **先分流再检索**：闲聊、缺事实、拒答不进知识库。
- **法律问必检索**：生成只依据召回片段，无依据则承认不确定。
- **检索可追溯**：关键结论能回到《法律名称》+ 条号。

### 1.2 请求总链路

```text
用户问题
    → 安全与空问过滤
    → 意图分流
          ├─ 闲聊 / 情绪 / 非法律 → 大模型短回复（不检索）
          ├─ 拒答 → 安全策略
          ├─ 信息不足 → 澄清追问（不检索）
          └─ 法律咨询 → 问题治理 → 混合双路召回 → RRF → Reranker → Top-K
                         → 提示词生成（强制引用）
```

## 二、RAG 离线（知识库）

### 2.1 目标

把现行有效的法律、行政法规、司法解释等切成可检索、可引用、带效力与地域元数据的块，用 **BGE-M3** 同时写入稠密向量与稀疏向量，供在线混合检索。向量库使用 **Milvus**。

### 2.2 分块策略与理由

法律文本层级为 **编 / 章 / 节 / 条 / 款 / 项**。「条」是引用和适用的最小完整单位。

**主策略：按「条」切分 + 上下文前缀 + 超长条按「款」再切（父子块）。**

| 层级 | 做法 | 理由 |
|------|------|------|
| 默认原子块 | 一条法律 = 一个检索块 | 能准确引用「第 n 条」；条件、但书同条完整 |
| 块前缀 | `《法律名称》｜效力｜第×章｜第 n 条` | 避免不同法中条号撞车 |
| 超长条 | 按款切 child，检索用 child，生成带回 parent 整条 | 整条入向量会稀释；只入款可能丢掉款间关系 |
| 元数据 | 效力、地域、位阶进 payload，用 filter | 现行有效、属地不靠模型猜 |
| 非条结构 | 释义/官方问答用 256～512 字窗口，重叠约 64 字 | 无条结构时才用滑动窗口 |

不采用纯固定长度切法典：易把相邻两条粘在一起或切断「前款」指代，百姓场景最怕 **引用错条**。

### 2.3 解析、编码与更新

入库抽出：法律名称、文号、公布/施行日期、是否现行有效、条号款号、地域、位阶、源文件哈希。已废止文本可入库，**默认 filter 排除**。

BGE-M3 输出 `dense` + `sparse`。payload 建议：`doc_id, law_name, article, paragraph, chunk_type, status, region, effective_date, parent_id, text`。

在线 query 编码必须与入库 **同一套 BGE-M3**。法规变更按文档替换或按条增量，并记录 `kb_version` 写入在线日志。

## 三、RAG 在线

### 3.1 意图分流

分级，避免每句都上大模型：

1. 规则：极短问候、明显情绪句 → 闲聊。  
2. 轻量分类：`闲聊 | 法律咨询 | 信息不足 | 拒答`。  
3. 边界不清再升大模型。

闲聊：短共情 + 说明能帮什么，**不编法条**。信息不足：先追问。法律咨询：进入问题治理与检索。

### 3.2 问题治理

一次结构化输出：是否多问、检索 query 列表、是否需要澄清。

| 情况 | 动作 |
|------|------|
| 一问多问 | 拆子问题，分别检索，分点作答 |
| 用语不规范 | 术语规范化后再检索，回答仍用白话 |
| 又长又乱 | 先归纳争议焦点再检索 |
| 多轮指代 | 结合历史改成独立完整问句 |
| 缺关键槽位 | 先澄清 1～2 个槽（地区、主体等） |
| 事实矛盾 / 对比问 | 分情景或改写适用关系 |
| 效力 / 时效 / 地方 | query 带意图；filter 带地域 |
| 情绪包裹 | 抽出法律事实再检索 |
| 代写诉状 / 教唆违法 | 拒答或降为程序指引 |

子问题过多（如 >3）时先让用户选优先问哪几个。

### 3.3 双路召回 → RRF → 重排

```text
query → BGE-M3 dense Top-K 与 sparse Top-K
      → 效力/地域过滤
      → RRF 融合（不直接加两路原始分）
      → Reranker（建议 BGE-Reranker）
      → Top-K（约 5～8）进提示词
```

稠密与稀疏分数量纲不同，融合用 **RRF**。法律场景「字面像、条件不像」的干扰条多，重排为必要步骤。同一 `parent_id` 可去重；生成尽量用 parent 全文。多子问题分别重排再按问分区拼进提示词。

### 3.4 生成与日志

约束：只根据片段回答；不足则不确定、不编条号；结论带《法》+ 条号；结构为结论 → 依据 → 白话 → 注意（时效/管辖/证据）→ 下一步指引；免责声明。改写/分类用小模型，最终回答用更强模型。日志记录治理类型、召回 ID、rerank 分、kb_version、耗时。

## 四、分期

**P0：** 按条分块 + 双向量入库；意图分流 + 单 query 混合召回 + RRF + Reranker + 带引用生成。  
**P1：** 问题治理全策略、父子块、地域 filter。  
**P2：** 学习排序、评测集（召回率、引用正确率）。

---

## 五、风险

错条比不答更严重，检索不足必须降级。地方与全国规定靠元数据 filter，不靠模型记忆。知识库不更新会造成系统性错误。
